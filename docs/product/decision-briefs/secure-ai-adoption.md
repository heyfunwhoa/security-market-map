# Decision brief: secure AI adoption

Status: educational candidate; human review pending. Owner: Market Map maintainer. Version: 0.1. Updated: 2026-11-06. Review due: 2026-12-04. No actual deployment, budget or ROI is asserted.

## Decision and outcome

Decide whether one AI-assisted workflow should move from experiment to bounded production. Desired outcome: improve a defined business task while maintaining acceptable quality, access boundaries and operating cost. Capability: evaluate outputs, control actions and operate the workflow with accountable ownership.

Illustrative trigger: a team wants to expand a pilot. Actual demand and urgency: Unknown. Separate drafting or recommendation from execution authority. Begin with the minimum actions needed, not a generic enterprise AI platform purchase.

## Alternatives and trade-offs

| Alternative | Potential value | Cost / limitation | Disqualifying evidence |
| --- | --- | --- | --- |
| Improve existing non-AI workflow | Lower complexity | May leave difficult work manual | Cannot meet the actual business requirement |
| Use incumbent AI capability | Existing integration path | Licensing and boundary constraints | Cannot demonstrate required controls or task quality |
| Buy specialist application | Focused workflow support | Supplier and data dependencies | Unsupported data handling or operating model |
| Build bounded workflow | Tailored behavior | Evaluation, engineering and ongoing maintenance | No accountable operational team |
| Use managed implementation / operation | Add skills | External access and retained internal accountability | Responsibilities or permissions cannot be agreed |
| Defer expansion | Preserve optionality | Delays potential benefit | A justified urgent need cannot be met another way |

## Dependencies and failure modes

Define the task, baseline, data rights, evaluation set, approved actions, escalation and cost allocation before scaling. Dependencies may include data cleanup and access ownership.

Test errors, unauthorized data access, excessive actions, cost spikes and unreliable outputs. Prevent the pilot from becoming production through informal use. Set human approval boundaries appropriate to the workflow, usage limits and a disable/rollback path. Stop expansion if critical controls fail or if task quality/cost misses agreed criteria. This is a validation proposal, not a security certification.

| Metric | Baseline | Target / decision rule | Method and owner | Observation window |

| Human review and rework | Unknown | Must be included in net productivity | Time sampling; operations owner | Pilot and follow-up |
| Full cost per successful task | Unknown | Competitive with relevant alternative | Include usage, licenses, review and maintenance; finance | Pilot and scale sensitivity |
| Boundary failures | Unknown | Defined critical failures stop expansion | Authorized evaluations; security/application owners | Before release and after material changes |
| Adoption | Unknown | Sufficient intended use to realize benefit | Workflow usage and user feedback; process owner | Pilot and agreed follow-up |

Recommendation hypothesis: fund a bounded comparison before expansion. Time saved is capacity until actual expense reduction is substantiated. Do not infer revenue from usage. Validate higher-volume economics separately.
